# Дизайн: управление доской с телефона через локальный веб-сервер

Дата: 2026-09-24
Статус: черновик на ревью

## Контекст и цель

Gambit — настольное приложение (Electron + React + TypeScript). Нужно управлять игрой с телефона: приложение поднимает локальный веб-сервер и отдаёт страницу с доской. Ходы, сделанные на телефоне, применяются на доске в приложении; позиция из приложения отображается на телефоне. Удалённая доска — полное зеркало текущей позиции приложения.

Домен и правила живут в renderer-процессе (`ADR 0001`, `ADR 0002`). Порт может слушать только `main`, поэтому сервер поднимается в `main`, а состояние синхронизируется по IPC. Это ровно то следствие, о котором предупреждал `ADR 0002` («когда понадобится доступ к ресурсам — границу придётся пересматривать и вводить IPC»).

## Не-цели

- На телефоне нет списка ситуаций, комментариев, статуса, сброса и бота — только доска текущей позиции.
- Нет аутентификации: доступ открыт всей локальной сети (осознанный выбор).
- Нет превращения кроме ферзя (как и в текущей версии приложения).
- Нет сохранения партий и истории ходов на сервере.

## Архитектура

Три процесса:

- **renderer** — единственный источник истины: `Chess` в `useChessGame`, `playMove`, текущий FEN.
- **main** — HTTP + WebSocket сервер и IPC-мост. Правил шахмат в `main` нет.
- **удалённая страница** — отдельный renderer-entry (React + `react-chessboard` + `chess.js`), локальное зеркало позиции.

Потоки данных:

1. При старте renderer публикует текущий FEN в `main`.
2. Телефон подключается по WS, `main` сразу отдаёт ему последний FEN.
3. Дроп на телефоне: страница проверяет ход локальным `chess.js`, применяет его у себя и шлёт интент в `main`.
4. `main` пересылает интент в renderer; renderer применяет ход через `chess.js`; принятый ход меняет позицию.
5. Renderer публикует новый FEN; `main` рассылает его всем клиентам — обе доски синхронизируются.
6. Ход в приложении работает так же: renderer публикует FEN, `main` рассылает.

## IPC-протокол

Типизированный, через `preload` → `window.api.remote`:

- `remote:position` (renderer→main, `send`): `{ fen: string }` при каждом изменении позиции и на монтировании.
- `remote:move` (main→renderer, `on`): `{ from: string; to: string; promotion?: string }` от клиента.
- `remote:server-info` (renderer→main, `invoke`): `{ url: string; port: number; qrDataUrl: string } | null`.

`preload` дополнительно отдаёт `onRemoteMove(callback)` с функцией отписки.

## WebSocket-протокол

JSON, путь `/ws`:

- сервер→клиент при подключении и при каждом изменении позиции: `{ type: 'position', fen: string }`;
- клиент→сервер: `{ type: 'move', from: string; to: string; promotion?: string }`.

Ack нет: клиенты синхронизируются из широковещательных `position`.

## Веб-сервер

- Порт по умолчанию `3210`; если занят — следующий свободный в диапазоне `3210–3219`; реальный порт отдаётся в UI.
- Слушаем `0.0.0.0`, чтобы телефон в локальной сети мог подключиться.
- HTTP отдаёт страницу и ассеты:
  - prod — файлы из `out/renderer` (`remote.html` + чанки);
  - dev — проксируем на Vite dev-server (`ELECTRON_RENDERER_URL`): `/` → `${ELECTRON_RENDERER_URL}/remote.html`, ассеты — с того же dev-server, чтобы работал HMR.
- WebSocket на пути `/ws`, навешен на тот же HTTP-сервер.
- LAN-адрес: первый не-внутренний IPv4 из `os.networkInterfaces()`; иначе `localhost`.
- Страница определяет WS-адрес как `ws://${location.hostname}:<wsPort>/ws`, где `wsPort` — `location.port` (prod) или `?wsPort=` из dev-редиректа.
- Статика отдаётся с защитой от выхода за каталог (path traversal).
- Сервер поднимается в `app.whenReady()` и закрывается при выходе.

## Удалённая страница

- Новый entry: `src/renderer/remote.html` + `src/renderer/src/remote/main.tsx`, монтирующий `<RemoteBoard />`.
- В `electron.vite.config.ts` renderer добавляется `build.rollupOptions.input` с двумя точками входа (`index`, `remote`).
- `RemoteBoard`:
  - держит локальный `Chess` (зеркало); на `{ type: 'position', fen }` заменяет его на `new Chess(fen)` и перерисовывает доску;
  - `onPieceDrop`: пробует ход локально через `chess.js`; если легален — обновляет локальную позицию и шлёт `{ type: 'move', from, to, promotion: 'q' }`; иначе возвращает `false`;
  - рендерит `react-chessboard`, превращение — в ферзя;
  - при обрыве WS переподключается с backoff; при реконнекте сервер сразу присылает актуальную позицию;
  - Electron-API не использует.
- Вёрстка рассчитана на телефон: доска занимает `min(100vw, 100vh)` с небольшим отступом.

## UI: адрес и QR

- В правом нижнем углу правой панели — круглая иконка-кнопка без текста (`QrCode` из `lucide-react`), абсолютное позиционирование (`.right-panel { position: relative }`).
- Клик открывает модалку (оверлей, крупный крестик, закрытие по `Esc`) с большим QR-кодом и адресом `http://<ip>:<port>/`.
- QR генерируется один раз в `main` пакетом `qrcode` как data-URL и отдаётся в renderer через `remote:server-info`.
- Пока адрес недоступен — кнопка неактивна.

## Зависимости

- `ws` — WebSocket-сервер в `main` (де-факто стандарт).
- `qrcode` — генерация QR в `main`.

## Обработка ошибок и крайние случаи

- Порт занят → следующий свободный; если весь диапазон занят — сервер не поднимается, кнопка QR неактивна, причина пишется в лог.
- Нет LAN-IPv4 → показываем `http://localhost:<port>/`.
- Нелегальный ход с телефона → `chess.js` отклоняет, страница возвращает фигуру назад, рассылки нет.
- Мат/пат/ничья → `playMove` вернёт `false`, позиция не меняется, клиенты остаются на текущей.
- Несколько телефонов одновременно → ходы применяются renderer'ом последовательно, каждая рассылка синхронизирует всех.
- Обрыв WS → переподключение с backoff, при реконнекте приходит актуальная позиция.
- Смена ситуации или сброс в приложении → публикуется новый FEN, удалённая доска обновляется.
- Renderer не готов / окно закрыто → сервер хранит последний FEN; пришедшие ходы отбрасываются до следующей публикации.

## Тестирование

- Конфиг Vitest переводим на `test.projects`: проект `renderer` (jsdom + текущий `setup.ts`) и проект `main` (`environment: 'node'`), иначе node-тесты `main` падают из-за `window` в setup.
- `remoteServer` (main, node): сервер на эфемерном порту (`0`), `ws`-клиент. Проверяем: при коннекте приходит текущая позиция; `broadcastPosition` рассылает позицию; ход клиента вызывает `onMove`; запрос статики отдаёт HTML; path traversal блокируется.
- `useRemoteBridge` (renderer): с моком `window.api.remote` — публикует позицию на монтировании и при изменении, вызывает `playMove` на `remote:move`, отписывается при размонтировании.
- `RemoteBoard`: с мок-WebSocket — рендерит позицию из `{ type: 'position' }`, шлёт ход при дропе, обновляется на новое сообщение.
- Кнопка QR: неактивна без адреса; клик открывает модалку с QR и адресом; закрытие по крестику и `Esc`.
- Прогон: `npm test`, `npm run lint`, `npm run typecheck`.
